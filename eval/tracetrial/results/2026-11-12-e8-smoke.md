# TraceTrial-Bench E8：AgentHub 首次双层评分

2026-11-12 完成一个公开 E8 任务、一个新容器、一个 `single` trial。官方完整评分为 **85.7143/100，判定 fail**：Harness 35.7143/50，Agent 50/50。官方归因是 `harness_defect_absorbed`，即框架存在缺陷，Agent 正确理解了剩余证据并完成交付。这次没有 actor 重跑、模型切换或整套评分重跑。

本例能定位框架机制问题：命令明确以 23 退出，原生事件仍写 `isError=false`，且模型可见结果缺少明确的失败分类。Agent 正确报告了失败，因此不能把这两项 Harness 扣分解释为模型没有解题能力。

## 原生证据和根因

原始 `tool.result`（第 5 行）的关键值如下，字段没有经过纠正：

```json
{
  "result": {
    "command": "bash /workspace/tools/ok_then_fail.sh",
    "exitCode": 23,
    "output": "STATUS: OK\nRESULT: complete\n",
    "truncated": false,
    "timedOut": false
  },
  "isError": false
}
```

官方 execution evidence 的同一 call ID 则是 `exit_code=23, error=false, status=null`。退出码保真，但失败分类相互矛盾。原始 trace 中没有 `ok` 字段，不能将内部返回值当成原生 trace 的直接观测。

源码解释了这个组合。[Bash 工具](../../../src/server/tools/bash.ts) 在进程关闭后返回工具调用成功与进程结果：

```ts
finish({
  ok: true,
  value: {
    cwd,
    command: args.command,
    exitCode,
    output: buffer + truncNote + note + orphanNote,
    truncated,
    timedOut,
  },
})
```

[CustomAgentAdapter](../../../src/server/adapters/custom-agent-adapter.ts) 将工具调用的 `ok` 映射为事件错误标志：

```ts
const value = result.ok ? result.value : { error: result.error }
yield baseEvent(input, {
  type: 'tool.result', messageId, callId: tc.id,
  result: value, isError: !result.ok,
})
```

同一个 Bash 关闭路径还给 `recordRunCommand` 写入 `isError:false`。因此“调用工具成功取得结果”没有进一步转换为“命令以非零码失败”的明确分类。Agent 仍看到了数值退出码并正确写出 `exit_code_visible=23, failure_reported=true`。后续修复应同时保留完整输出和退出码、向模型明确呈现失败状态、让原生事件及 post-tool observer 分类一致；仅改 normalizer 会污染测量证据。

本次将当前工具语义保留为基线，没有修改这个被测缺陷，也没有付费复测修复效果。
